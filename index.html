Understanding Distributed Training: From DDP to FSDP Through a Communication Lens

How do thousands of GPUs coordinate to train a 70-billion-parameter model? The answer lies in three collective communication primitives and one elegant decomposition.

Training modern large language models requires far more memory and compute than any single GPU can offer. The field has developed a rich set of parallelism strategies to distribute this work across many devices. Yet it can be hard to see the forest through the trees: ZeRO-1, ZeRO-2, ZeRO-3, DDP, FSDP, ring all-reduce… the terminology multiplies quickly.

This post takes a deliberate, narrow focus: we will understand distributed training through the lens of communication. Starting from a single GPU, we will build up to FSDP, and at each step ask only one question — what communication happens, and why?

1 · Single-GPU Training — The Baseline

Before distributing anything, let's carefully establish what happens on a single GPU. A training iteration has three phases, and understanding the layer-by-layer flow through each phase is essential — it is exactly this pattern that DDP and FSDP will later distribute across many devices.

Forward Pass — Activations Build Up Layer by Layer

The forward pass feeds input x through the network one layer at a time. At each layer l, two operations happen in sequence: a linear transformation, then a non-linearity:

zl = Wl · al−1 + bl   (linear)   →   al = σ(zl)   (non-linearity)

The crucial fact: every intermediate activation al must be kept in GPU memory. Why? Because the backward pass will need each one to compute the weight gradient for that layer. Step through the animation below to watch activations accumulate layer by layer.

Backward Pass — Chain Rule Through Every Layer

The backward pass reverses direction. Starting from the scalar loss ℒ, gradients propagate right → left through each layer. At every layer l, the chain rule produces two quantities:

Two outputs per layer in the backward pass
①
∂ℒ/∂Wl = δl · al−1T — weight gradient (uses the stored forward activation!)
②
δl−1 = WlT · δl ⊙ σ′(zl−1) — upstream gradient passed leftward via chain rule
where δl = ∂ℒ/∂zl is the gradient of the loss w.r.t. the pre-activation at layer l.

The chain rule is what makes deep learning trainable: instead of computing a giant Jacobian of the full network, we apply the same local rule at every layer and pass the result along. Each layer only needs to know the gradient arriving from the right, not anything about layers further downstream.

Optimizer Step

With all parameter gradients computed, the optimizer updates every weight. Adam maintains two exponential moving averages per parameter: the first-moment estimate m and the second-moment estimate v. Together they adaptively scale the learning rate for each parameter:

mt = β₁mt−1 + (1−β₁)g  ·  vt = β₂vt−1 + (1−β₂)g²  ·  θ ← θ − η · m̂t / (√v̂t + ε)
Activation Memory — The Other Half of the Budget

During the forward pass, every intermediate tensor must be kept alive until the corresponding backward computation — the chain rule requires it. This activation memory is proportional to batch size, not model size, and is completely independent of how parameters are distributed. ZeRO-1/2/3 and FSDP all leave activation memory untouched.

In practice, activation memory ranges from a few GB to tens of GB per GPU, depending on sequence length, batch size, number of layers, and attention implementation. Standard attention has a quadratic O(s²) term that dominates at long sequences; FlashAttention eliminates it, substantially reducing the footprint. 2 · Data Parallel Training (DDP)

The simplest way to use multiple GPUs is to replicate the model on each one and split the data across them. This is Data Distributed Parallel (DDP), and it is the foundation of nearly all distributed training.

The DDP Protocol

Suppose we have N GPUs. At the start of training, every GPU holds an identical copy of the full model. Each iteration proceeds as follows:

Each GPU holds at rest
Params 2 B/param full copy
Gradients 4 B/param full copy
Opt states 8 B/param full copy
Activations A/N ≈ 12·(b/N)·s·h·L bytes — not reduced by ZeRO
Total 14 B/param + A/N replicated N times
1
Forward pass
The dataset is split across N GPUs. Each GPU runs a forward pass on its own mini-batch and computes a local loss. Activations are saved layer by layer (A/N total). No communication needed.
2
Backward pass
Each GPU runs the full backward pass and produces a local gradient. These differ per GPU because each saw a different mini-batch. We need every GPU to end up with the same averaged gradient before the optimizer step.
All-Reduce 2× model
All GPUs exchange and sum their gradients. Every GPU ends up with the same averaged gradient — identical everywhere. Under the hood this is Reduce-Scatter + All-Gather.
3
Optimizer step  no communication
Every GPU runs the optimizer on the full averaged gradient. Because all GPUs have exactly the same gradient and the same parameters, the optimizer step is identical everywhere. All model replicas stay in sync without any additional communication.

The critical insight is step 4: because every GPU computes a gradient on a different mini-batch, the gradients differ. We need every GPU to end up with the same gradient (the average across all GPUs) so that the optimizer step keeps all model replicas identical. This is exactly what All-Reduce achieves.

Why average, not sum? DDP semantics are equivalent to training on a single GPU with a batch size of N × local_batch_size. Taking the average gradient is numerically equivalent to computing the gradient on the full joined batch.

3 · All-Reduce — The Communication Primitive Behind DDP

All-Reduce is a collective operation where every participant starts with a local tensor and ends up with the element-wise reduction (sum, average, max…) of all participants' tensors. After an All-Reduce, every GPU has the same result.

4 GPUs, each holding a local gradient vector with 4 chunks [A, B, C, D]. Values differ per GPU (A₀ ≠ A₁ ≠ A₂ ≠ A₃) — each GPU computed on a different mini-batch. Click Next ▶ to step through the All-Reduce.

Why Not Just Reduce to One GPU and Broadcast?

A naïve implementation would route all tensors to a single GPU (a "parameter server"), sum them, and broadcast the result back. This bottlenecks on the root GPU's bandwidth. The ring All-Reduce algorithm, popularized by Baidu Research, arranges GPUs in a logical ring and pipelines data chunks in both directions, achieving close to ideal bandwidth utilization regardless of N.

The decomposition into Reduce-Scatter + All-Gather is not just an implementation detail — as we will see, it becomes the design blueprint for FSDP.

4 · Why DDP Is Not Enough — Memory Explosion

DDP works well when the model fits on a single GPU. The entire training state — parameters, gradients, and optimizer states — is replicated on every device. This replication is the problem.

For a 7B model, each DDP replica requires ~98 GB of training state alone — more than a single A100 (80 GB) can hold. Activations add a further 3–20 GB on top. For a 70B model the training state alone grows to ~980 GB. DDP simply cannot be used here.

The core problem DDP replicates the full training state on every GPU. For large models, this redundancy is not just wasteful — it makes training impossible. Activations compound the problem further: they cannot be reduced by parameter sharding.

Figure 2. DDP replicates the full training state (parameters, gradients, optimizer states) on every GPU. FSDP shards all of it: each GPU holds only 1/N of each component. With 8 GPUs and a 70B model, per-GPU memory drops from ~980 GB to ~123 GB.

5 · ZeRO and FSDP — Sharding to the Rescue

The ZeRO (Zero Redundancy Optimizer) paper by Rajbhandari et al. (2020) made the key observation: DDP's redundancy is a choice, not a necessity. All three components of the training state can be sharded, and different stages of sharding trade memory for communication.

Figure 3. ZeRO stages progressively shard more of the training state. ZeRO-3 (= PyTorch FSDP) shards parameters, gradients, and optimizer states. Memory per GPU scales as O(1/N).

ZeRO-1: Optimizer State Sharding

Adam maintains two fp32 momentum buffers per parameter — m (first moment) and v (second moment) — totalling 8 bytes per parameter. These are the single largest memory consumer in a mixed-precision setup. ZeRO-1 shards them: GPU k is responsible for the optimizer states of parameter shard k only.

The complete training step under ZeRO-1 is:

Each GPU holds at rest
Params 2 B/param full copy
Gradients 4 B/param full copy
Opt states 8/N B/param 1/N shard ← ZeRO-1
Activations A/N same as DDP — not reduced
1
Forward pass
Every GPU has a full copy of the model, so forward runs exactly like DDP. Activations are saved along the way for use in the backward pass.
2
Backward pass
Each GPU runs the full backward pass and produces a complete local gradient. These differ across GPUs because each processed a different mini-batch. ZeRO-1 syncs them the same way as DDP — an All-Reduce — but here we make the two internal steps explicit:
Reduce-Scatter 1× model
Each GPU sends its gradient chunks to the GPU responsible for that chunk, which sums all incoming copies. Afterwards, every GPU holds one small but correctly averaged gradient shard.
All-Gather 1× model
Every GPU broadcasts its averaged shard to all others. Afterwards, every GPU holds the complete averaged gradient — identical everywhere. Total backward cost: 1× + 1× = 2× model size, same as DDP.
3
Optimizer step  no communication
Every GPU has the full averaged gradient, but each only runs the optimizer on its responsible slice, using the optimizer state shard it already owns. After this step, each GPU's slice is correctly updated — but no single GPU has a complete, up-to-date model yet.
4
Parameter sync
All-Gather 1× model
Each GPU broadcasts its freshly updated slice. Afterwards, every GPU holds the complete, fully updated model and is ready for the next forward pass.

ZeRO-2: Gradient Sharding

ZeRO-2 adds gradient sharding on top of ZeRO-1. To understand why it works, it helps to first ask: can we compute only part of the gradient? The answer is no. Backpropagation is a sequential chain-rule computation — to get the gradient for layer l, you must first propagate δ backward through all later layers. There is no shortcut. Every GPU must run the full backward pass.

This is exactly why ZeRO-2's design is elegant: rather than trying to split the computation, it splits the storage. Each GPU computes the complete gradient, but instead of keeping it, a Reduce-Scatter immediately sums across all GPUs and delivers each GPU only its responsible shard. The full gradient tensor never needs to land in memory — it is summed and discarded in one step.

Each GPU holds at rest
Params 2 B/param full copy
Gradients 4/N B/param 1/N shard ← ZeRO-2
Opt states 8/N B/param 1/N shard
Activations A/N same as DDP — not reduced
1
Forward pass
Every GPU has the full model, so forward runs exactly like DDP. Activations (A/N) are saved for the backward pass — same footprint as DDP.
2
Backward pass
Each GPU runs the full backward pass — there is no way to compute only part of the gradient, since backpropagation requires a complete pass through the entire network. The local gradients differ per GPU. Instead of All-Reduce, ZeRO-2 uses only the first half:
Reduce-Scatter 1× model
Each GPU sends its non-owned gradient chunks to the responsible owner, which sums them. Every GPU ends up with one correctly averaged gradient shard. The other chunks were computed but are immediately dropped — the full gradient tensor never needs to exist in memory.
3
Optimizer step  no communication
Each GPU runs the optimizer on its gradient shard using its local optimizer state shard. All three quantities — gradient, momentum, and variance — are the same 1/N slice, so they align perfectly. No communication needed.
4
Parameter sync
All-Gather 1× model
Each GPU broadcasts its freshly updated parameter shard. Every GPU ends up with the complete updated model. Total communication this step: 1× + 1× = 2× model — identical to DDP.

ZeRO-3 / FSDP: Parameter Sharding

ZeRO-3 shards the parameters themselves — this is the level that PyTorch's Fully Sharded Data Parallel (FSDP) implements. Each GPU holds only 1/N of the parameters at rest. Because no GPU has the full model, both the forward and backward passes must now temporarily reconstruct each layer's parameters on demand, layer by layer.

Each GPU holds at rest
Params 2/N B/param 1/N shard ← ZeRO-3
Gradients 4/N B/param 1/N shard
Opt states 8/N B/param 1/N shard
Activations A/N same as DDP — ZeRO does not reduce this
Total 14/N B/param + A/N model states scale linearly with N
1
Forward pass — layer by layer
No GPU has the full model, so parameters must be reassembled one layer at a time. For each of the L layers:
All-Gather  (per layer) 1/L × model each
All GPUs contribute their shard of this layer's weights, temporarily reconstructing the full layer. The layer is computed, activations are saved, then the full weights are immediately discarded — only the local shard is kept.
L layers × All-Gather = 1× model total
2
Backward pass — layer by layer
Processed in reverse order. For each layer, the weights were discarded after the forward pass and must be re-fetched before the gradient can be computed. Each layer then produces two distinct gradients with very different fates:
All-Gather  (re-fetch weights) 1/L × model each
The full layer weights are reconstructed again — they were discarded after the forward pass to save memory. With the full weights available, two gradients can now be computed for this layer.
∂ℒ/∂x  (activation gradient — passed to previous layer) full, not sharded
The gradient with respect to this layer's input. This is the upstream signal that chain rule passes to layer l−1 — without it, the previous layer cannot compute its own gradients. It must remain complete on every GPU; no communication is performed on it.
∂ℒ/∂W — Reduce-Scatter  (weight gradient — sharded immediately) 1/L × model each
The gradient with respect to this layer's weights. Each GPU has a local copy; they are summed across GPUs and scattered — each GPU keeps only its owned shard. The rest is dropped immediately. No single GPU ever stores the full weight gradient. The full layer weights are then discarded again.
L layers × (All-Gather + Reduce-Scatter) = 2× model total
3
Optimizer step  no communication
Each GPU updates its own parameter shard using its gradient shard and optimizer state shard — all three are the same 1/N slice. Fully local. No All-Gather needed afterwards because the updated shards will simply be re-fetched layer by layer during the next forward pass.

FSDP Communication Flow — Forward and Backward

With parameters sharded, FSDP must orchestrate communication around every layer to temporarily assemble the full parameters needed for computation, then discard them to recover memory. Here is the full training step traced end to end.

Figure 4. Complete FSDP training step. Forward: one All-Gather per layer. Backward: one All-Gather (re-fetch) + Reduce-Scatter per layer. The optimizer step is fully local. Full parameters exist in memory only during each layer's compute window.

Forward pass: Before each layer, FSDP triggers an All-Gather to reconstruct the full parameter tensor W_l from the N shards. Once the layer's output is computed and activations are saved, the full weights are immediately freed — only the local shard is kept. Parameters exist in memory only during each layer's brief compute window.

Backward pass: Layers are processed in reverse. For each layer, FSDP re-fetches the full weights via another All-Gather — they were discarded during the forward pass. With the full W_l available, two gradients are computed: the upstream ∂L/∂x (passed to the previous layer, kept full on every GPU) and the weight gradient ∂L/∂W_l (immediately handed to a Reduce-Scatter — summed across GPUs and sharded, so each GPU retains only its slice). Activations are freed layer by layer as they are consumed.

The elegant symmetry Forward uses All-Gather to assemble parameters layer-by-layer. Backward uses Reduce-Scatter to distribute gradients layer-by-layer. Both operate on tensors of the same size as the parameter tensor for that layer.

FSDP trades a modest increase in communication volume (~3/2× compared to DDP) for a dramatic reduction in peak memory (scales as 1/N). On high-bandwidth interconnects (NVLink, InfiniBand), this trade-off is nearly always worthwhile for models that do not fit in GPU memory under DDP.

6 · Summary — Three Primitives, One Training System

We have traced the full path from single-GPU training to FSDP, and at every step the story was told by three collective communication operations.

The Three Communication Primitives

All-Reduce
Every GPU starts with a local tensor; every GPU ends with the element-wise sum. Used in DDP to synchronize gradients after the backward pass. Internally decomposes into Reduce-Scatter followed by All-Gather.
All-Gather
Each GPU contributes its shard; every GPU ends with the full tensor. Used in FSDP forward (and backward) to reconstruct full parameter tensors layer-by-layer before computing each layer.
Reduce-Scatter
Each GPU contributes a local tensor; the sum is computed and scattered — each GPU receives a unique shard of the result. Used in FSDP backward to aggregate and distribute gradient shards.
The unifying identity All-Reduce ≡ Reduce-Scatter + All-Gather. DDP applies this once per training step at the global level. FSDP applies the two halves separately, once per layer — the same total work, distributed through time, enabling memory to stay bounded at O(1/N).

The Design Principle

What makes FSDP elegant is that it does not invent new communication primitives — it reuses the same All-Gather and Reduce-Scatter that together constitute the All-Reduce you already know from DDP. The key insight is simply to move these operations from the iteration level to the layer level, allowing parameters to be temporarily materialized and immediately reclaimed.

Communication Overhead — ZeRO vs DDP

A common misconception is that all ZeRO stages add communication overhead. They do not. ZeRO-2 replaces DDP's All-Reduce with a Reduce-Scatter, eliminating the All-Gather that DDP performs mid-backward — the total communication volume is identical to DDP. Only ZeRO-1 and ZeRO-3 carry extra overhead.

Strategy Communication per step vs DDP Memory saved (N=8)
DDP 2× |model| — —
ZeRO-1 3× |model| +50% Opt states ÷ 8
ZeRO-2 2× |model| 0% ✓ Grads + opt states ÷ 8
ZeRO-3 / FSDP 3× |model| +50% Params + grads + opt ÷ 8

ZeRO-1 is rarely the best choice: it adds 1× communication overhead while ZeRO-2 achieves greater memory savings at zero extra cost. In practice, the decision is usually between DDP, ZeRO-2, and ZeRO-3.

When to Use Each Strategy

DDP Model fits on one GPU
The full training state (14 B/param) fits within each GPU's memory budget. All GPUs hold full replicas.
Example: fine-tuning a 3B model on 8× A100 (80 GB each) — 3B × 14 B ≈ 42 GB, well within budget.
ZeRO-2 Model almost fits — try this first
Parameters fit but gradient + optimizer state memory overflows. ZeRO-2 shards both at zero communication overhead vs DDP — the same 2× |model| per step.
Example: training a 13B model on 4× A100. DDP needs 182 GB per GPU; ZeRO-2 (N=4) cuts model states to ~45 GB — fits with room for activations.
ZeRO-3 / FSDP Model does not fit even with ZeRO-2
Even the parameters alone exceed per-GPU memory. ZeRO-3 shards everything — params, grads, and optimizer states — trading a 50% communication increase for linear memory scaling with N. No single GPU ever holds the full model.
Example: training a 70B model on 8× A100. ZeRO-2 needs ~245 GB per GPU (params alone 140 GB); ZeRO-3 reduces model states to ~24.5 GB per GPU — fits, at 3× |model| communication per step.
