§0The 134 GB Problem

The setupWhy every DML optimization exists in the first place

You have an H100 with 80 GB of memory. You want to train a 7B-parameter Transformer with Adam. Let's count bytes:

Fig 0.1 · The starting problem. Every technique in this guide exists to close this 54 GB gap, then push it further.

"Distributed training" isn't one technique. It's a sequence of escapes, each one made necessary by hitting a wall the previous solution couldn't cross.

That's exactly the path we'll walk. The story ahead has nine chapters, and each begins by hitting a wall:

Two single-GPU tricks (mixed precision and activation checkpointing) close the gap before we even leave one card. Once we add more GPUs, the journey continues:

  1. You add a second GPU → suddenly you need to sync gradients
  2. The sync is now your bottleneck → hide it behind compute
  3. The model triples → even a sharded replica won't fit → ZeRO/FSDP
  4. One layer won't fit → tensor + pipeline parallelism
  5. You span multiple nodes → the network has tiers
  6. Communication is still the wall → compress it
  7. You need to actually tune all this → roofline + decision tree
  8. You want one mental model that explains everything

Mixed precision · stop using fp32

fp32 = 4 bytes per number. bf16 = 2 bytes. Same dynamic range as fp32 (same 8-bit exponent), just less mantissa precision. Modern GPUs run bf16 matmul on TensorCores at 2 to 4× the FLOPs of fp32. One config flag, half the memory, faster compute.

Fig 1.1 · bf16 keeps fp32's full range; it just gives up some precision. For training, range matters far more than the 16th decimal place.

Adam keeps a fp32 master copy of the weights to avoid drift across many small updates. The compute and storage during the forward/backward use bf16. This is what torch.autocast(dtype=torch.bfloat16) wires up automatically.

Activation checkpointing · trade compute for memory

For a 7B model with batch 4 and sequence 8192, activations alone are ~22 GB, the orange bar in Fig 0.1. They dominate everything else combined for long contexts. Where do they come from?

To do backward, autograd needs the input of every layer. Naively, you save every intermediate tensor in the forward. With L layers and a batch of activations at each, you store O(L) tensors.

The trick: save only every k-th layer's input. For the layers in between, recompute the forward pass during backward. You spend ~30% more FLOPs and save 5 to 10× the activation memory.

The animation below walks through one full step. Forward (green): the data flows through 4 layers grouped into two segments, but only checkpoint inputs (★) are kept in memory. Backward (red): when the gradient arrives at a non-checkpointed segment, the segment's forward is re-run from the saved checkpoint to materialize the activations needed, then backward proceeds.

Fig 1.2 · Activation checkpointing animated. Green = forward, red = backward. Watch the recompute flashes (⟲) when backward enters a segment whose intermediates were thrown away.

In PyTorch this is one wrapper:

from torch.utils.checkpoint import checkpoint

class TransformerBlock(nn.Module):
    def forward(self, x):
        return checkpoint(self._forward, x, use_reentrant=False)
✓ Single-GPU optimizations · summary

bf16 alone takes 134 → ~70 GB. Add activation checkpointing → ~50 GB. The 7B model now fits with margin. We've solved §0 without writing a single line of distributed code.

§1The birth of AllReduce

OptimizationsData parallelism (DDP) · Ring AllReduce · bandwidth-optimal collectives

A 7B model trains. Now you want it to train twice as fast, so you buy a second H100. The moment you have two GPUs, you have a problem you didn't have before: they have to agree.

The simplest plan: replicate the model

Put a copy of the model on each GPU. Feed each GPU a different micro-batch. Each one computes a different gradient. To stay in sync, you average the gradients before stepping the optimizer. This is data parallelism.

The new question: how do you average gradients across GPUs?

The bad answer: parameter server

The obvious thing: pick one GPU as the "server." Everyone sends it their gradient, it sums, broadcasts back. Done. Right?

Fig 2.1 · The parameter server's central node receives N times the gradient. Ring AllReduce avoids the bottleneck by spreading the work.

The good answer: ring AllReduce

Arrange the GPUs in a logical ring. Split each GPU's gradient into N equal chunks. The algorithm runs in two phases:

Phase 1 · ReduceScatter. Over N−1 steps, each GPU sends one chunk to its right neighbor and receives one from its left. It adds the received chunk to its own. After N−1 steps, GPU i holds the fully-reduced version of chunk i, and only chunk i.

Phase 2 · AllGather. Another N−1 steps of the same rotation, but now passing along the reduced chunks instead of summing. After this, every GPU has every reduced chunk. Done.

Watch it run. Every step has 4 chunks transmitting simultaneously — one packet on each of the ring's four edges, in parallel. As packets arrive, the receiving cell inside each GPU updates: during ReduceScatter, the cell's label progresses x → x⁺ → x⁺⁺ → Σx as the partial sum accumulates. After RS step 3, every GPU owns one fully-reduced Σ chunk. Then AllGather takes 3 more parallel steps; after each AG step, one more cell inside each GPU lights up green Σ, until all 4 cells on all 4 GPUs hold the full reduced gradient.

Fig 2.2a · Ring AllReduce animated, fully parallel. Each of the 6 steps shows 4 simultaneous chunk transmissions, one per ring edge, color-coded by sender (G0 blue, G1 pink, G2 purple, G3 amber). RS steps 1–3 reduce; after step 3 every GPU owns one fully-reduced Σ chunk. AG steps 1–3 (all 4 packets green) circulate the Σ chunks until every GPU holds all four.

The static walkthrough below shows the precise chunk states at each step of Phase 1 if you want to verify the math:

2(N−1)/N × M bytes per GPU. As N grows, this approaches 2M, independent of the number of GPUs. That's the magic.
Fig 2.2 · Ring AllReduce phase 1, walked through. Each step every GPU sends one chunk and receives one. After 3 steps (=N−1), every GPU owns a fully reduced chunk.

This is what NCCL implements when you call dist.all_reduce(). For tiny messages, NCCL uses a tree topology instead (lower latency); for large ones, ring (better bandwidth). You don't choose; NCCL detects your topology at init and picks.

📐 The bandwidth model worth memorizing

T_allreduce = α + 2(N-1)/N × M / B  ·  α = launch latency, M = message bytes, B = link bandwidth, N = ranks.

Two implications: (1) for large M, the cost approaches 2M/B regardless of N: that's why DDP scales. (2) For small M, α dominates: that's why we batch into buckets (next section).

§2Hiding the wire

OptimizationsBackward overlap · Bucket fusion · async NCCL streams

AllReduce works. But naively, the GPU sits idle while it runs. With 8 GPUs and a 7B model, the wire dominates 30 to 40% of every step. We have two levers to hide it.

The naive timeline · half the GPU is wasted

Without any tricks, each step looks like this:

Fig 3.1 · The single biggest lever in distributed training. Whatever your topology, overlap turns a sum into a max.

Lever #1 · Backward overlap

Gradients become ready in reverse order during backward (last layer first). The moment layer L's gradient is computed, you can kick off its AllReduce on a separate CUDA stream. The GPU keeps computing layer L−1's backward while the wire moves layer L's gradient. This is what DDP does by default.

You don't write any of this; it's wired up by:

model = DDP(model, gradient_as_bucket_view=True)
# ↑ that's it. Backward overlap is on by default.

Lever #2 · Bucket fusion

Backward overlap alone has a problem: a transformer has thousands of small parameter tensors. If you AllReduce each one separately, you pay the launch latency α every time. With α ≈ 5 μs and 1000 tensors, that's 5 ms of pure launch overhead per step.

The fix: concatenate small gradients into a "bucket" until the bucket reaches a target size, then AllReduce the whole bucket as one message.

Fig 3.2 · Bucket fusion saves (N − 1) × α per step by amortizing launch overhead across many small gradients. But the bucket size itself is a trade-off: too small and α-cost returns; too large and the bucket can't ride the overlap with backward. PyTorch DDP defaults to 25 MB — a balanced sweet spot.

PyTorch DDP buckets automatically. The default bucket_cap_mb=25 works for most networks; tune it if your profile shows either many tiny messages (grow it) or comm finishing after backward (shrink it).

✓ After §2

You have data parallelism that scales near-linearly to dozens of GPUs. DDP + bf16 + activation checkpoint is what 90% of fine-tuning workloads use, and it's enough up to ~7B models on 8×H100.

If your model fits with this setup, you can stop reading. The next sections solve problems that don't exist yet.

§3When the model doesn't fit

OptimizationsFSDP · ZeRO-1 / ZeRO-2 / ZeRO-3 · AllGather + ReduceScatter · forward / backward prefetch

You upgrade from 7B to 70B. The math from §0 scales linearly: now you need ~1.3 TB. Even with bf16 + activation checkpoint, a single GPU can't hold the model. DDP is dead. But look closer at what DDP was holding…

The waste hiding in DDP

In DDP, every GPU stores a full copy of params, grads, and optimizer states. With 8 GPUs that's 8× redundancy. A 70B model in DDP needs 1.3 TB on every GPU. Insanity.

"If you can't fit the whole model, stop holding the whole model."

The idea: shard everything across GPUs. Each GPU owns 1/N of the params, 1/N of the grads, 1/N of the optimizer states. To compute a layer, gather just that layer's params from all GPUs (briefly, for that one layer), use them, then throw them away.

This is the ZeRO family of optimizations from DeepSpeed. PyTorch's FSDP is essentially ZeRO-3.

The ZeRO progression

ZeRO comes in three levels. Each shards more, saves more memory, costs more communication:

params, grads, optimizer — but NOT activations. Activations grow with batch × seq² and stay full on every GPU. The fix: activation checkpointing (~5–10× reduction) or sequence parallel (shards along seq dim). READING THE CHART Solid block = this GPU owns this 1/N slice. Dashed block = NOT held; must be gathered on demand. Per-row numbers below each block show GB on a 70B model with N=8 GPUs.
Fig 4.1 · The ZeRO progression. Activations are the blind spot — ZeRO doesn't touch them. Even with ZeRO-3 (FSDP), activations stay full on each GPU. To fit truly large models you need ZeRO-3 + activation checkpointing (or sequence parallel). PyTorch FSDP FULL_SHARD = ZeRO-3; SHARD_GRAD_OP = ZeRO-2.

The new comm pattern: AllGather → compute → ReduceScatter

FSDP changes the rhythm of every layer. Instead of "compute, then sync gradients at the end," each transformer block now does:

Fig 4.2 · FSDP's per-layer dance. The materialized weights live transiently; each GPU only persistently owns its 1/N shard.

Prefetching collectives · hiding the AllGathers (ZeRO-3 / FSDP only)

Two collectives per layer is a lot more comm than DDP. This is a ZeRO-3 / FSDP problem specifically — DDP, ZeRO-1, ZeRO-2 don't materialize layers on demand, so they don't need this trick. The saving grace for ZeRO-3: you can prefetch the next layer's weights while the current one is still computing.

Two prefetch directions, both controlled separately in PyTorch FSDP:

Fig 4.3 · Two prefetch directions in FSDP (ZeRO-3 only). The COMPUTE row and the COMM row run on separate CUDA streams; the comm boxes are placed UNDER the matmul they overlap with. Without prefetch, the comm boxes would slide right and become serial gaps. With both flags on, the wire is busy whenever the GPU is computing — per-layer collectives effectively become free.

PyTorch FSDP exposes three relevant knobs (only meaningful for FULL_SHARD / ZeRO-3):

from torch.distributed.fsdp import (
    FullyShardedDataParallel as FSDP,
    ShardingStrategy, MixedPrecision, BackwardPrefetch,
)

model = FSDP(
    model,
    sharding_strategy=ShardingStrategy.FULL_SHARD,    # ZeRO-3
    mixed_precision=MixedPrecision(
        param_dtype=torch.bfloat16,
        reduce_dtype=torch.bfloat16,                  # collective in bf16 too
    ),
    backward_prefetch=BackwardPrefetch.BACKWARD_PRE,  # most aggressive overlap
    forward_prefetch=True,                            # also overlap forward
    limit_all_gathers=True,                           # cap in-flight gathers
)
⚠️ The trade-off you signed up for

FSDP doesn't make training faster. It makes training possible for models that don't fit. You pay ~1.5× the comm of DDP for the privilege. Use it when you must, not when you can DDP.

§4Splitting the model itself · model parallelism

OptimizationsTensor parallelism (Megatron) · Pipeline parallelism · 1F1B schedule · 3D parallelism

FSDP gets you to ~70B–100B params on a typical cluster. Beyond that, you hit a different kind of wall: even with sharding turned all the way up, the model itself is too big to ride on data parallelism alone. The fix is to split the model, not the data — known collectively as model parallelism.

Model parallelism · the two ways to split a model

Data parallelism (DDP, FSDP) replicates the model and splits the data. Model parallelism does the opposite: it splits the model itself. There are two ways to split a model — and they fix two different failure modes.

The animation below shows what each one cuts. Watch the model start as a single block, then see how each style of parallelism slices it differently:

Fig 4.4 · Two flavors of model parallelism. Pipeline cuts the model horizontally — each GPU owns a contiguous range of layers. Tensor cuts each layer vertically — each GPU owns a column slice of the weight matrix. The two are orthogonal: real frontier-scale training combines both (plus DP).

Below we walk through pipeline first (simpler concept, historically first), then tensor (more involved, the technique that actually fixes the AllGather-peak failure from §3), then how to combine all three (DP, PP, TP) at frontier scale.

Pipeline parallelism · splitting the model along depth

Pipeline parallelism splits the model along its layers: with 80 layers and 4 stages, each stage owns 20 contiguous layers and lives on one GPU. A micro-batch enters stage 0, flows through stage 1 → 2 → 3, then activations come back the same way during backward.

The naive schedule has a problem: stages sit idle waiting for upstream data. The pipeline bubble:

Fig 5.2 · The naive GPipe schedule. All micro-batches go forward first, then all backwards. Stages later in the pipeline must wait while the first micro-batch propagates down (warm-up bubble), and earlier stages must wait for backward to climb back up (cool-down bubble). Idle time = wasted GPU.

1F1B (One Forward, One Backward) keeps the same total cells, but interleaves them so each stage alternates F and B as soon as it can. The overall bubble fraction is the same — but because backward starts earlier, activations are released sooner, cutting peak memory roughly in half:

Fig 5.3 · The 1F1B schedule. Only S3 (the deepest stage) alternates F·B·F·B cleanly — its B₀ starts at slot 5, immediately after F₀. The B₀ gradient then propagates upward one stage per slot: S2 at slot 6, S1 at slot 7, S0 at slot 8. So upper stages still have idle gaps between their backwards, waiting for B from below. The total bubble fraction is the same as GPipe — but because B starts earlier, F₀'s activation on S0 is released at slot 8 instead of slot 11. Peak activation memory is roughly halved.

Why micro-batch count matters: the cool-down idle gets filled as M ↑

Look back at Fig 5.3 — the dots in the middle of S0, S1, S2 are wasted GPU time. That waste shrinks as you increase the number of micro-batches per step: each extra micro-batch adds one more F to the front and one more B to the tail, but the "B propagating upward" cool-down stays the same length (it's fixed by P, the number of stages). So the bubble fraction:

bubble fraction = (P − 1) / (M + P − 1)

Fig 5.4 · The bubble fraction (P−1)/(M+P−1) for fixed P=4 stages. M=4 (what Fig 5.3 drew) is intentionally small for clarity — real training uses M=64 or higher, putting bubble overhead below 5%. Megatron's Interleaved 1F1B goes further: by chopping each stage into V virtual sub-stages, the formula becomes (P−1)/(V·M+P−1), shrinking the bubble by another factor of V.

Naive vs 1F1B · the full comparison

Pulling everything we've seen together, here's the side-by-side that explains why 1F1B is the production default for pipeline parallelism. Notation: P = pipeline depth (number of stages), M = micro-batches per training step, every F or B takes 1 time slot.

MetricNaive (GPipe)1F1B
Total time (slots, same M) 2M + 2(P−1) 2M + 2(P−1)
Theoretical bubble (same M) 2(P−1) 2(P−1)
Theoretical bubble fraction (same M) (P−1) / (M+P−1) (P−1) / (M+P−1)

Practical M (memory-limited) M ≈ P M = 64+

⚠ The two-level bubble story

Theoretical (same M): synchronous 1F1B has the same per-step bubble as GPipe — both are 2(P−1) idle slots, just distributed differently in the schedule.

Practical (real training): 1F1B's O(P) activation memory frees you to use much larger M (64, 128, ...). Plug a large M into (P−1)/(M+P−1) and the effective bubble drops to < 5% — that's why 1F1B feels like it has "less bubble" in production. The bubble formula didn't change; M did.

In other words: 1F1B's gift isn't a smaller bubble at the same M — it's the freedom to use a much larger M. Megatron's Interleaved 1F1B goes one step further by splitting each stage into V virtual sub-stages, shrinking the formula itself to (P−1)/(V·M+P−1).

Bubble doesn't change. Three other things do.

  1. Activation memory drops from O(M) to O(P). In naive, every micro-batch's activations are kept until backward eventually arrives. In 1F1B, activations are freed as soon as their B finishes — and at most ~P micro-batches are "in flight" at once. Reduction factor ≈ M/P.
    Example · P=8, M=32 → naive holds 32 activation sets · 1F1B holds ~8 → 4× less peak memory
  2. Backward latency drops from O(M) to O(P). The first gradient becomes available roughly P slots after the first F starts (not M slots later). This shortens the critical path of the optimizer step.
  3. GPU utilization in the middle is much higher. Naive's middle-section is empty waiting for the F-to-B transition. 1F1B fills that gap with interleaved F's and B's so every stage is busy almost every slot in steady state.
    util ≈ M / (M + P − 1) → 1.0 as M ≫ P

Same bubble. But activations bounded by pipeline depth, not micro-batch count. That's the whole reason 1F1B replaced GPipe in production.

✓ One-line summary

Naive: forward piles up → activations balloon → backward latency huge.
1F1B: backward fires as soon as F reaches the last stage → activations stay at O(P) → GPUs near-fully utilized.

Best case vs worst case · 1F1B's full spectrum

The formulas above are envelopes — where you actually land depends on three knobs:

  1. M (micro-batch count) — controls bubble fraction
  2. Stage balance — controls slowest-stage bottleneck
  3. Stage position — controls per-GPU activation imbalance (even within 1F1B)
⚠ WORST CASE · what kills 1F1B in practice
  • Small M (M ≈ P): bubble fraction climbs to (P−1)/(2P−1) ≈ 40–50% · same as GPipe, no real win
  • Unbalanced stages: if one stage takes 2× longer (e.g. layers split unevenly), the entire pipeline runs at the slowest stage's pace · total time = M × Tslowest
  • Long F+B per slot: if a single stage's compute is huge, the bubble's absolute time (2(P−1) slots) becomes painful in wall-clock terms
  • Cross-DC pipeline: if PP stages span data centers and activation transfer is slow, the "F→F→F→F" propagation alone takes seconds per slot
✓ BEST CASE · what frontier training actually achieves
  • M ≫ P (M = 64, 128, 256+): bubble fraction drops below 5%, often below 2%
  • Balanced stages: layers per stage tuned so each stage takes the same F+B time (often non-uniform · early stages get more layers because their activations are smaller)
  • Interleaved 1F1B (Megatron): V virtual sub-stages per GPU multiply the denominator → (P−1)/(V·M+P−1)
  • NVLink/IB topology: PP runs on the slowest tier safely because activations between stages are small

The hidden activation imbalance

Here's a subtlety most people miss: 1F1B's "O(P) activation memory" is averaged — the per-stage distribution is not uniform. Earlier stages hold more in-flight activations because the F's they did first are still waiting for B to climb back up.

Fig 5.5 · 1F1B's hidden activation imbalance. The total in-flight activations are bounded by O(P), but per-stage they follow peak(j) = P − j — S0 sits at the bottleneck, Slast has spare memory.

Tensor parallelism · splitting the matmul itself

Pipeline parallelism solves the "total model is too big" case by spreading layers across GPUs. But it doesn't solve the harder case: a single layer is too big to fit on one GPU even temporarily. That's the AllGather-peak failure from §3, redrawn here for reference:

Recall what FSDP does on every layer's forward (Fig 4.2): it briefly AllGathers the full layer's weights on every GPU, runs the matmul, then frees them. At small scale, the temporary materialization is invisible. At 175B, each transformer block is ~5 GB of weights, and that 5 GB spike stacks on top of the already-near-capacity sharded state plus activations.

OOM during the AllGather, not at steady state. Sharding doesn't help here — the spike is the layer itself.
Fig 5.0 · The failure mode at frontier scale. FSDP's per-layer AllGather temporarily materializes the full layer's weights on every GPU. When a single layer is too big to spike on top of the baseline, sharding more doesn't help — you have to split the layer itself.

Sharding shrinks the baseline. It doesn't shrink the spike.

The escape is to not materialize the layer at all. Slice the matmul itself across GPUs so no single device ever holds a complete layer's weights — each just owns a piece of W and computes its share of the multiplication. The math composes back to the original answer at the end.

TP has exactly two ways to slice a matmul

For any single matmul Y = X · W, tensor parallelism gives you exactly two splitting strategies. Both are mathematically exact (we'll prove it below); they differ in which dimension of W gets cut, and that determines whether the layer needs a full input or a sharded input.

① Column-parallel② Row-parallel
W split along columns (output dim) rows (contraction dim)
Required input full · replicated · cannot be sharded sharded · cannot be full
Output sharded · ready for next layer partial · needs AllReduce to be full
Comm at output none AllReduce(sum)

The input requirement is the constraint to internalize:

  • Column-parallel needs a full (replicated) X: each GPU multiplies the same X by its column slice of W. Hand it a sharded X and the math breaks.
  • Row-parallel needs a sharded X: each GPU's slice of X must pair with its row slice of W. A replicated X just wastes work.

This input/output mirroring is exactly what makes column → row compose without intermediate communication (the Megatron sandwich, two sections down). For now, here is each flavor on its own.

① Column-parallel · split W along the output dim

Each GPU keeps a column slice of W and uses the (replicated) X to compute its own slice of Y. Concretely on two GPUs: GPU 0 holds W[:, :d/2], GPU 1 holds W[:, d/2:]. Both multiply by X. Each produces its own half of Y. The output is naturally sharded — no comm needed, and the next layer can consume those halves directly.

Fig 5.1 · Column-parallel matmul. W is sharded across GPUs by columns; X is replicated; Y is sharded. Forward stays comm-free — each GPU's matmul is fully local. The dual flavor (row-parallel) is next.

② Row-parallel · split W along the contraction dim

The dual move. Split W along its row dimension k (the contraction axis) so GPU 0 holds the top rows W[:k/2, :] and GPU 1 holds the bottom rows W[k/2:, :]. The input X must be sharded along its column dimension k to match — each GPU's X_i pairs with its W^row_i. Each GPU multiplies and produces a partial Y of the full output shape. AllReduce(sum) at the end combines the partials into the full Y on every GPU.

Fig 5.1b · Row-parallel matmul. X is sharded across GPUs along the contraction dim k; W is split row-wise so each GPU's row block of W pairs with its X shard. Each GPU computes a partial Y locally (X₀·W₀ on GPU 0, X₁·W₁ on GPU 1) — same shape, different values. AllReduce(sum) combines the partials into the full Y on every GPU. The math proof comes next.

Why row-parallel is mathematically equivalent · the math proof

Column-parallel is "obvious" — each GPU computes a different output slice, and concatenating gives the full Y. Row-parallel is more subtle: each GPU computes a partial output, and we claim that summing partials gives the exact full matmul. Let's prove that.

Let X be (b × k), W be (k × m), and Y = X · W of shape (b × m). Element-wise, the standard definition of matrix multiplication is:

Y[i, j]  =  Σ_{ℓ=0}^{k−1}  X[i, ℓ] · W[ℓ, j]      ← contraction sum over ℓ

Now partition the contraction index ℓ into N equal groups, one per GPU. GPU n owns the slice ℓ ∈ [n·k/N, (n+1)·k/N). Sums distribute over partitions, so:

Y[i, j]  =  Σ_{ℓ=0}^{k−1}  X[i, ℓ] · W[ℓ, j]
         =  Σ_{n=0}^{N−1}  ⎡  Σ_{ℓ ∈ group n}  X[i, ℓ] · W[ℓ, j]  ⎤
                          ⎣                  ─────────────────  ⎦
                                    this inner sum = (X_n · W_n)[i, j]
         =  Σ_{n=0}^{N−1}  (X_n · W_n)[i, j]

where X_n = X[:, group_n_indices] (shape b × k/N) and W_n = W[group_n_indices, :] (shape k/N × m). Each GPU computes its own block product X_n · W_n entirely locally:

Y  =  X_0 · W_0  +  X_1 · W_1  +  ...  +  X_{N−1} · W_{N−1}
                              ↓
                        AllReduce(sum)

That's the entire proof: matrix multiplication's contraction sum partitions cleanly across the contraction dimension, and addition is associative. No approximation, no clever tricks — just the basic algebra of inner products. The result is bit-identical to single-GPU computation (modulo the floating-point ordering of the AllReduce, which differs by O(machine epsilon) in practice).

This same logic — partition the contraction, compute local block products, sum at the end — is the foundation of every collective-style matmul in the literature (TP, sequence parallel, Ring/Block matmuls). Once you've seen it once, all of them are the same proof with different partitioning.

What does each TP flavor cost in real practice?

The two flavors are mirror images. We'll walk through column-parallel first (forward and backward), then row-parallel, then put the two costs side by side and explain why their composition into a sandwich is the cheapest possible arrangement.

Pattern A · standalone column-parallel · forward + backward

Column-parallel splits the OUTPUT dimension of W. Each GPU holds the full replicated X and its column shard W_col_i, and computes its own slice Y_i = X · W_col_i locally. Nothing crosses the wire in forward. The output Y is naturally sharded across GPUs (each holds its slice).

Backward is where comm shows up. Each GPU sees only its slice of ∂L/∂Y and computes its own contribution to ∂L/∂X via ∂L/∂Y_i · W_col_i^T. Each contribution has the FULL shape of X but is a partial sum (only one GPU's contribution). To recover the full replicated ∂L/∂X (which is what the upstream layer needs, since X was replicated), the contributions are summed across GPUs via AllReduce. One collective per col-parallel layer, in backward only.

Fig 5.1d · Real practice for a column-parallel layer. Forward produces sharded Y on each GPU with no comm. Backward produces partial ∂L/∂X on each GPU and AllReduces it into the full replicated gradient.

Takeaway for column-parallel: 0 collectives in forward, 1 AllReduce in backward, and this cost is paid by every col-parallel layer in the model (not amortized, not deferrable). Now let's see what happens when the matrix is split the other way.

Pattern B · standalone row-parallel · forward + backward

Row-parallel splits the INPUT dimension of W (the contraction dimension). Each GPU holds only a column slice X_i of the input and a row shard W_row_i of the weights, and computes X_i · W_row_i = partial Y. The partial Y has the FULL output shape on every GPU, but it's only one GPU's contribution to the sum; to recover the full Y, partials are summed via AllReduce. So forward already costs 1 collective, unlike col-parallel.

Backward is symmetric. ∂L/∂Y arrives full on every GPU. Each GPU computes its own slice ∂L/∂X_i = ∂L/∂Y · W_row_i^T locally. These slices are non-overlapping pieces of the full input gradient. Since the original X was replicated (every GPU saw the same X in forward), the upstream layer needs the full replicated ∂L/∂X back, which means combining the slices via AllReduce again. Two collectives total per row-parallel layer.

Fig 5.1e · Real practice for a row-parallel layer. Forward produces partial Y on each GPU and AllReduces into the full Y. Backward produces a per-GPU slice of ∂L/∂X and AllReduces into the full replicated input gradient. Two collectives per layer.

Takeaway for row-parallel: 1 AllReduce in forward, 1 AllReduce in backward, every layer. Twice as many collectives as col-parallel, again paid by every row-parallel layer in the model.

Side by side · column-parallel vs row-parallel standalone

With both flavors walked through, here are the per-layer costs of running them standalone (M = activation size = batch × hidden; AllReduce on a ring ≈ 2M bytes per GPU):

LayerForward commBackward commCollectives per layer
Column-parallel (single) none AllReduce on ∂L/∂X · ≈ 2M 1 (backward only)
Row-parallel (single) AllReduce on Y · ≈ 2M AllReduce on ∂L/∂X · ≈ 2M 2

Two clean observations:

  1. Row-parallel is twice as expensive per layer as column-parallel, because it pays AllReduce in both directions while column pays only in backward.
  2. The shapes don't compose symmetrically. Column outputs sharded Y; row consumes sharded X. That is, row's input shape exactly matches column's output shape. This is not an accident, and it's the hint that there's a way to combine them that costs less than running either alone twice.

That observation is the bridge to the next section.

The Megatron sandwich · why column → row composes for free

Here's the elegant observation that powers Megatron-LM: column-parallel's sharded output is exactly the sharded input that row-parallel needs. Stack a column-parallel layer immediately before a row-parallel layer and the two compose with zero communication between them — the only AllReduce in the whole sandwich is the one at the very end of the row-parallel layer.

Fig 5.1c · The Megatron sandwich, animated forward → backward. Forward: X (replicated) flows through the column-parallel layer (no comm), the sharded Y feeds straight into the row-parallel layer, and the partial Z is AllReduced into the full Z. Backward: ∂L/∂Z (full) flows back through the row-parallel layer (no comm), the sharded ∂L/∂Y feeds the column-parallel backward, and the partial ∂L/∂X is AllReduced into the full replicated gradient. 2 AllReduces total for 2 matmuls · same per-matmul cost as a single column-parallel layer.
Now the full three-way comparison

With the sandwich on the table, here is where AllReduce fires in each pattern, side by side:

Fig 5.1f · Comm timeline for each pattern. AR = AllReduce, ≈ 2M bytes per GPU on a ring (M = activation size). The sandwich packs 2 matmuls into 2 collectives, matching col-parallel's per-matmul cost while doing twice the work.

The punchline. Two row-parallel layers run independently would cost 4 collectives (2 per layer × 2 layers). Two column-parallel layers would cost 2 backward collectives, and would still need an extra collective between them in forward to reshape the sharded output back into a replicated input. The col → row sandwich packs two matmuls into the same collective budget as a single row-parallel layer: 1 AllReduce in forward, 1 in backward, total 2 collectives for the pair. Per matmul that is half the wire bill of the next-best option, and exactly the same as a single col-parallel layer (which already had the lowest cost per matmul of the standalone choices).

Two structural wins reinforce this:

  1. Sharded passes through. Column-parallel's output is sharded along the same dimension that row-parallel expects its input to be sharded along. No reshuffle, no AllGather, no ReduceScatter between the two matmuls.
  2. Comm sits at the block boundary. The forward AllReduce lands at the very end of the sandwich, the backward AllReduce at the very start. Both are clean synchronization points that can overlap with the next or previous block's compute, instead of fragmenting comm in the middle of a matmul pair.

And conveniently the sandwich is exactly what transformer architecture already gives you (attention's QKV → output, MLP's up → down, both expand-then-contract pairs). The cheapest TP composition is also the architectural default.

Per layer, not per first layer. The collective costs above apply to every layer of that flavor in the model, not just the first one. A real transformer with N blocks (each block holding 2 col → row sandwiches: attention QKV → output and MLP up → down) pays 2N AllReduces in forward + 2N AllReduces in backward = 4N AllReduces per training step. The first or last layer is not special. Note: the collective is AllReduce, not AllGather. AllGather (concat shards into a full tensor) and ReduceScatter (sum partials and scatter) are different collectives that don't appear in standard col → row TP at all.

3D parallelism · combining all three

Three orthogonal sharding axes. The relationship is not sequential replacement; the three axes are layered on top of each other in the same layer execution. The cleanest way to introduce them is by what each one actually shards.

FSDP · shards STORAGE (data parallel + intra-group sharding)

All GPUs are split into FSDP groups (the data-parallel groups). Each group is one logical model replica. Within a group, the parameters, gradients, and optimizer states are sharded across the GPUs (ZeRO-3 style); each GPU only stores its 1/N portion of the state, never the full thing. Different groups process different mini-batches (this is the data-parallel part). Solves: "the model state doesn't fit on one GPU."

TP · shards COMPUTE (within a single layer)

Within a single layer, the matmul is sliced across multiple GPUs (the col → row sandwich we just covered). Multiple GPUs jointly compute that one layer in parallel. TP decides how to parallelize the compute within this layer. Solves: "this single layer's matmul is too big or too slow on one GPU."

PP · shards LAYERS (pipeline)

The model is cut into stages along its layer dimension. Each GPU (or group of GPUs) only owns some of the layers. Micro-batches are pipelined through the stages so all stages stay busy. PP decides who computes which layers. Solves: "I have too many layers and / or I want better device utilization through pipelining."

The standard recipe (concrete example: 8 GPUs as FSDP=2 × PP=2 × TP=2):

  1. Outer axis · 2 FSDP groups, each = 1 logical replica with 4 GPUs. Each GPU stores 1/4 of that replica's params + grads + optimizer states (ZeRO-3). The two groups process different mini-batches in parallel (data parallelism).
  2. Inside each FSDP group · PP=2: the 4 GPUs are split into 2 pipeline stages of 2 GPUs each (Stage 0 holds layers 0…L/2, Stage 1 holds layers L/2…L).
  3. Inside each PP stage · TP=2: the 2 GPUs of the stage run the col → row sandwich on every layer they own.

Storage is sharded across the FSDP group (all 4 GPUs jointly hold one replica). Compute is organized as PP × TP within the group. The figure below walks through this exact 8-GPU configuration end to end.

Fig 5.7 · Concrete 8-GPU example · FSDP=2 × PP=2 × TP=2. Top: FSDP storage band shows each group holds one full replica, sharded into 4 pieces (1/4 per GPU). Middle: the 4 GPUs of each group are organized as 2 PP stages × TP=2 for compute. Animation: ① FSDP AllGathers the current layer's params within each group → ② Stage 0 fires its TP sandwich → ③ activations flow to Stage 1, which fires its TP sandwich → ④ backward + FSDP ReduceScatter grads back to per-GPU shards. The two FSDP groups process different mini-batches in parallel.
What happens for each layer · the per-layer execution loop

The three axes don't run in series at the model level (e.g. "first do all of FSDP, then all of TP"). They interleave per layer. Each layer's forward pass looks like this:

for each layer in the model:
    if PP: skip if this stage doesn't own this layer

    # ① FSDP fetches this layer's full params from its shards
    full_W = AllGather(my_shard_of_W)      # within FSDP group, on IB

    # ② TP runs the col → row sandwich on full_W, parallel across the TP group
    output = TP_compute(input, full_W)     # 1 AllReduce on NVLink

    # ③ FSDP releases the gathered copy, keeps only the shard
    free(full_W)

    # backward later, symmetric:
    #   TP backward gives partial grads
    #   ReduceScatter(grads) within FSDP group → each GPU keeps its grad shard

Three things to notice. First, this happens layer by layer: at any moment only one layer's params are gathered to full size, which is the whole point of FSDP's memory savings. Second, FSDP and TP both do their work in the same layer execution: FSDP supplies the params, TP parallelizes the compute on those params. They don't conflict. Third, PP simply gates whether a given device participates in this layer at all, based on which pipeline stage owns the layer.

Two common confusions worth correcting.

1. "After AllGather you can't compute in parallel." Wrong. After FSDP's AllGather brings the full layer params onto every GPU in the group, that is exactly when TP fires the parallel computation. AllGather supplies the data; TP parallelizes the work on it. They cooperate, not conflict.

2. "TP and PP exist to solve the AllGather problem from FSDP." Inaccurate. AllGather is the comm cost FSDP pays for its memory savings; TP and PP do not directly fix it. They solve different problems entirely:

  • FSDP introduces AllGather (and the transient memory of the gathered copy) as the price of sharding storage.
  • TP solves compute parallelism within a layer. Independent of FSDP.
  • PP solves pipeline utilization across layers. Independent of FSDP.

Correct mental picture: FSDP gathers params → TP computes on them in parallel → FSDP releases the gathered copy. Three axes, three independent responsibilities, layered cleanly in the same per-layer execution.

One-sentence summary: FSDP defines data parallelism and shards the model state (solves storage); TP parallelizes compute within a layer (solves single-layer compute); PP pipelines layers across stages (improves throughput). Each layer is "FSDP first fetches the params, TP computes in parallel, PP decides whether this device executes at all."

FSDP · shards params (storage). TP · shards compute (within a layer). PP · shards layers (pipeline).

You don't typically write 3D parallelism by hand. Megatron-LM, DeepSpeed, and TorchTitan implement these schedules; you configure them. But the two most influential frameworks, Megatron-LM and FSDP / ZeRO, attack different problems and end up being complementary. Worth understanding what each is actually for.

Megatron vs FSDP · what each solves and how they complement

Both Megatron and FSDP shard things across GPUs. The crucial difference is what they shard and which problem that solves.

Megatron-LM (NVIDIA) shards the compute. Specifically, it splits each matmul along the output (column-parallel) or contraction (row-parallel) dimension. The col → row sandwich we just walked through is its core trick. The problem Megatron solves is "this single matmul is too big or too slow on one GPU." Each GPU now holds only a slice of W and computes only a slice of Y. Activations are also sharded as a consequence, which saves activation memory linearly with TP size. Megatron also implements pipeline parallelism for splitting layers across stages. Megatron's natural home is inside a node, on NVLink, because TP fires AllReduce on every layer and needs the fastest possible interconnect.

FSDP / ZeRO (Meta / DeepSpeed) shards the storage. The full computation still runs on full tensors, but each GPU only stores a slice of the parameters, gradients, and optimizer states (1/N each, where N is the FSDP group size). When a layer needs to compute, FSDP AllGathers the full weight just-in-time, runs the matmul, then drops the gathered copy. The problem FSDP solves is "the model state (params + grads + optimizer states) doesn't fit on one GPU." For Adam, optimizer state is 8 bytes per param vs 2 bytes for the param itself, so just sharding optimizer state (ZeRO-1) already saves 5×. FSDP's natural home is across nodes, since its comm pattern is bandwidth-bound but latency-tolerant.

Why they're complementary, not competing

Megatron alone cannot scale beyond a node. TP needs NVLink, and a single node usually has 8 GPUs. So Megatron fixes "matmul too big" but not "model too big to fit even after sharding the matmul."

FSDP alone wastes compute when the matmul itself is the bottleneck. FSDP gathers the full W on each GPU and runs the full matmul there, which means activation memory is not reduced and the matmul is not sped up by parallelism, only memory pressure is relieved.

The combination TP within node + FSDP across nodes is the standard recipe for frontier-scale training. TP shards each matmul among 8 GPUs on NVLink (handling the per-layer compute and activation memory). FSDP shards the model state across the cross-node DP dimension on IB (handling the total storage). Add PP on top if the model is so deep that even FSDP can't fit a single layer's worth of state on a node. Llama 3 used FSDP-only configurations for some training runs (the model was small enough that TP wasn't needed); GPT-scale models use all three.

Decision rule of thumb. If your bottleneck is "this matmul is slow" or "activations don't fit," reach for TP / Megatron. If your bottleneck is "I can't even allocate the optimizer state," reach for FSDP / ZeRO. If both: TP within node, FSDP across nodes, PP wherever bandwidth gets thin.

§5The network is not flat

OptimizationsTopology-aware placement · TP→NVLink · DP→IB · PP→WAN

Up until now we've imagined "the wire" as a single uniform thing. But once you span more than one node, the network has tiers, with bandwidth differing by orders of magnitude.

This is where the most expensive scaling mistakes happen. Place TP (which talks every layer) on a slow tier and you can lose 5× throughput.

Fig 6.1 · Three network tiers spanning ~3 orders of magnitude in bandwidth (900 → 25 → 1 GB/s). Each tier zone has the bar in the middle, with the bandwidth label inside and the comparison-to-NVLink to the right (no overlap). The bar width is log-proportional to bandwidth. Faster tier = wider bar; the heaviest comm (TP) gets pinned to the fastest tier (NVLink).

Why this works mathematically: TP runs every layer's AllReduce. With 80 layers and a 1 GB activation, that's 80 GB of comm per step. On NVLink (900 GB/s), that's ~90 ms, invisible. On IB (25 GB/s), that's 3.2 seconds, and your training is now 10× slower.

DP, by contrast, AllReduces only the parameter gradients (~70 GB for 70B model) and only once per step. That fits comfortably on IB. PP only sends activations between adjacent stages: small, infrequent, can survive WAN.

§6When comm is still the wall

OptimizationsGradient compression · quantization · top-K · SignSGD · PowerSGD · error feedback

For most workloads, bf16 + bucket fusion + overlap is enough. But sometimes (federated training, slow inter-DC links, extreme-scale models) you need to shrink the bytes themselves.

Four families of compression

Fig 7.1 · Four compression families on a single 8-element gradient. Each row keeps the same five-column structure (method · visual · size · ratio · note) so the trade-offs read across cleanly. Quantization is free and ubiquitous; Top-K, SignSGD and PowerSGD give 100× to 256× ratios but each demands a recovery mechanism.

The catch: error feedback

All lossy compressors share one trap: dropped information accumulates. Without correction, training diverges. The fix is mechanical and applies to every lossy compressor:

error = 0
for step in training:
    g = compute_gradient()
    g_corrected = g + error            # add last step's residual back in
    g_compressed = compress(g_corrected)
    error = g_corrected - g_compressed # remember what we dropped
    all_reduce(g_compressed)
    update(g_compressed)

Without this loop, top-K and sign-based methods are unstable. With it, they're surprisingly robust. Error feedback is the secret that makes the math work.

⚠️ When NOT to compress

For typical training on a fast cluster (NVLink + IB), bf16 is enough. The other techniques shine in federated, multi-DC, or extremely large-N settings. Reach for them last, not first.

Tuning discipline

The single rule that separates good engineers from bad: change one knob at a time, profile, compare. Never change three things and guess. Always keep a baseline run for comparison. Use torch.profiler or NVIDIA Nsight Systems; staring at nvidia-smi is not profiling.

TL;DR · 10 points grouped by stage

Where the problem comes from

  1. The wall. A 7B model + Adam needs ~134 GB. An H100 has 80 GB. Every technique here exists to close some version of that gap.

Single GPU first

  1. Defaults you should already have. bf16 + activation checkpoint already get you a 7B model on one GPU. Do this before adding any GPUs.

Communication primitives

  1. Ring AllReduce is bandwidth-optimal: 2(N−1)/N × M bytes per GPU, flat in N for large messages.
  2. Hiding the wire. Backward overlap + bucket fusion turn a sum into a max. This is what DDP does for free.

Scaling out

  1. Big models. FSDP / ZeRO-3 shards params, grads, optimizer state. AllGather + ReduceScatter per layer instead of one AllReduce per step. ~1.5× the comm of plain DDP.
  2. Even bigger. TP splits matmuls within a layer (NVLink only). PP splits layers across stages (1F1B schedule). Combine: TP within node × PP across nodes × FSDP across replicas.
  3. Topology rule. Heaviest comm to fastest tier. TP → NVLink, DP / FSDP → IB, PP → IB or WAN. Inverting this costs ~5×.

Last-resort tools

  1. Compression. Only when bf16 isn't enough. Always pair with error feedback or training diverges.
  2. Tuning workflow. Profile first. Use the decision tree. Change one knob at a time.

  1. One frame for the whole field. Every technique does one of three things: less data, fewer times, hide it. Classify a new paper by which of these three it answers.
