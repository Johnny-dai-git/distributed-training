Why Your 7B Model Won't Fit on 8 GPUs — And How ZeRO Fixes It

You bought 8 × A100s. 80 GB each. 640 GB of pristine HBM, ready to train. You launch your 7B model. It OOMs.

This is the most common surprise in LLM training, and the math behind it is short. A 7B model in mixed-precision Adam needs 14 bytes per parameter. That's 98 GB per GPU under plain DDP — already past the 80 GB cap, before activations or batches. Your 640 GB cluster can't even hold one full optimizer state.

This article shows where those 14 bytes come from, why DDP makes the situation worse instead of better, and how ZeRO removes the redundancy that creates the wall.

Where the 14 bytes go

Mixed-precision Adam stores each parameter four ways:

  • 2 bytes · bf16 weight used by forward and backward
  • 4 bytes · fp32 master copy for stable updates
  • 4 bytes · fp32 Adam first moment (momentum)
  • 4 bytes · fp32 Adam second moment (variance)

Total: 14 bytes per parameter, per GPU. For 7B params that is 98 GB. For 70B it is 980 GB. No single GPU on earth holds 980 GB — and DDP would need to replicate that storage on every GPU in the cluster. The math simply doesn't work past a certain size.

ZeRO removes the redundancy in three stages

Rajbhandari et al. asked the obvious question: why does every GPU need a full copy of everything? The answer is that it doesn't. The 14 bytes can be split across the cluster instead of replicated. Each ZeRO stage shards a different slice of those bytes.

ZeRO-1 · shard optimizer state. The two fp32 Adam moments (8 of the 14 bytes) get split across GPUs. Memory drops to roughly 6 + 8/N bytes per parameter. Communication rises ~50% over DDP because the optimizer step now needs an AllGather. Rarely the best choice — ZeRO-2 dominates it.

ZeRO-2 · shard optimizer state + gradients. Add the 4-byte gradient buffer to the sharded list. Memory drops further to ~3.5 bytes per parameter on N=8. The surprising part: communication stays exactly the same as DDP. The DDP AllReduce gets reorganized into a ReduceScatter (during backward) plus an AllGather (during optimizer step), totaling the same bytes. Free memory savings. This is almost always the first move when DDP can't fit.

ZeRO-3 (FSDP) · shard everything, including the parameters. Memory now scales as 14 / N bytes per parameter. A 70B model on 8 GPUs goes from 980 GB to ~24 GB per GPU — fits on a single A100 with room to spare. The cost is one extra collective per layer in forward (AllGather the params just-in-time, drop the gathered copy after compute). Total comm rises ~50% vs DDP, but the storage win is the only thing that lets very large models fit at all.

The insight most tutorials miss · two gradients, not one

ZeRO-3 reconstructs each layer's parameters on the fly during forward and backward. People often miss what happens to the gradients during backward. Each layer produces two gradients, and they're treated very differently:

  • ∂ℒ/∂x · the activation gradient. This is what flows down the chain rule into the previous layer. Stays full on every GPU. No communication.
  • ∂ℒ/∂W · the weight gradient. Computed locally on each GPU, then immediately ReduceScatter'd back to the per-GPU shards. No GPU ever holds the full weight gradient at any point.

This is why FSDP's communication budget is "1× model in forward + 2× model in backward = 3× model" rather than 4× — the activation gradient doesn't need a collective. Knowing which gradient costs comm and which doesn't is the difference between debugging FSDP and just guessing at it.

When to use which

The decision is short:

  • DDP first, if the full replica fits on each GPU. Lowest comm, simplest semantics.
  • ZeRO-2 the moment DDP OOMs. Free memory upgrade, identical comm.
  • ZeRO-3 (FSDP) when ZeRO-2 still doesn't fit. Pay 1.5× the comm to unblock the model size.
  • Skip ZeRO-1. ZeRO-2 has the same comm cost and strictly more memory savings.

What ZeRO doesn't solve

Sharding the model state across data-parallel replicas only attacks the storage axis. Two other axes exist, and once your model gets big enough, you'll need them on top:

  • Tensor parallelism · shard the matmul itself across GPUs in a node, on NVLink. Solves "this single layer is too big to compute on one GPU."
  • Pipeline parallelism · place different layer ranges on different stages, schedule them with 1F1B. Solves "the model has too many layers."

FSDP, TP, and PP are orthogonal: storage, compute, layers. The frontier-scale recipe is FSDP across nodes × TP within node × PP wherever bandwidth runs out, and the topology rule that decides which goes on which network tier is the difference between training in 9 days and 90.
